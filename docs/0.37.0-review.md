# RustWTM 0.37.0 release scope and validation

## Scope

**Core placement** ([design](core-placement.md)) and the Telegram, Memory
Guard and installation changes in the [changelog](../CHANGELOG.md).
IPC moves to protocol 19 (the status carries the core plan): a 0.36
service and a 0.37 window refuse each other until both are updated; the
MSI updates both.

- `[[pin]]`, `[[separate]]` and `[[reserve_cores]]` entries in
  `config.toml`. `wtm-policy`'s `Placer` makes one plan from them and the
  rescue core each sample: by physical core, fastest first, the rescue core
  first, then reserved cores, separation groups and pins; a constraint that
  would leave a process no processor is skipped and reported. Splits and
  reservations wait `hold_secs` (5 s) before they start and outlast a
  short exit as long, so short-lived helpers do not reshuffle them.
- The service's rescue core is the executor of that plan. It writes CPU
  Sets (hard affinity for `strict` entries in one processor group), at most
  500 processes a tick, and leaves alone processes that chose their own
  processors (CPU Sets of their own, or a narrower affinity, which Windows
  honours over CPU Sets). What it wrote is recorded in
  `%ProgramData%\RustWTM\placement.json` before it is written; a restart
  gives back what a crashed run left.
- Measured on Windows 11 build 26300 before building on it: a child process
  does not inherit its parent's default CPU Sets (hard affinity it does),
  running threads follow a changed process default, and affinity wins over
  CPU Sets. Entries therefore count what an app starts as part of it
  (`tree`, on by default).
- `wtm cores` shows the plan under the processor layout, `wtm cores explain
  <pid>` why a process has its processors.
- A Cores page under Protect, in all 26 languages: processor tiles with who
  holds each, the processes placed and why, and an editor for *Keep on
  cores*, *Keep apart* and *Reserve cores* that runs the plan on the apps
  running now before an entry is saved.

## Verification

`cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`,
`cargo doc` with warnings denied and the workspace tests pass on the
developer host (1208 passed, 23 ignored); the core-placement commits were
also built and tested alone in a separate worktree (1206 passed).
`scripts/ci/test-install-lifecycle.ps1` and `scripts/ci/verify-release.ps1
-Tag v0.37.0` pass. CI adds 0.36.4 as an upgrade baseline, with the
SHA-256 of its published MSI.

New tests:

- `wtm-policy`: the plan (pins with and without `tree`, splits by weight
  and fastest first, the hold, reserved cores leaving one core for the
  rest, the rescue core taken out, skipped constraints, processes that
  chose their own cores, uniform machines), core lists and their TOML,
  validation, and the TOML-preserving entry editors.
- `wtm-service`: the rescue core's three tests unchanged against the new
  executor; with a recording writer, a split written once and undone, a
  refusal not retried, strict affinity, dry run, the per-tick bound, the
  crash record given back, and the rescue core and entries in one plan; and
  a real `ping` process pinned and released.
- `wtm-cli`: `explain` and the plan listing, and the layout without a
  service.
- `wtm-gui`: the page with a plan, adding with preview, editing into another
  kind and removing, an incomplete entry, and placement reasons translated.

The Cores page was rendered in English, Turkish and German, light and
dark, wide and compact; two rows that overflowed a compact German window
were split.

Not covered: a machine with more than one processor group or more than 64
logical processors (hard affinity refuses them; CPU Sets are used), and
the page in the Indic, Asian and Swahili languages beyond the catalog
checks.
