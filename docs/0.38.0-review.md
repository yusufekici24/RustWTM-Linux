# RustWTM 0.38.0 release scope and validation

## Scope

**App power** ([design and measurements](app-power.md)) and two rule
actions, after a comparison with Process Lasso. IPC moves to protocol 20:
a 0.37 service and a 0.38 window refuse each other until both are updated;
the MSI updates both.

- `[[while_running]]` entries in `config.toml` and an *App power* page
  under *Protect*. While one of an entry's programs runs, and for
  `hold_secs` (5 s) after, the service switches to the entry's power plan
  and keeps the computer from sleeping; with `keep_awake = "display"` the
  RustWTM window keeps the screen on, also while it sits in the tray.
- Measured before building on it (Windows 11 build 26300): a power request
  from session 0, as the service runs, is accepted for the system and
  refused for the display (`ERROR_NOT_SUPPORTED`); from the user's session
  both are accepted.
- One keeper in the service owns the power plan. Game mode asks for High
  performance like an entry does; game mode first, then the entries in the
  order of the file. The plan in use before the first switch is written to
  `power-plan.txt` before switching and comes back when no request is
  left, or at the next start after a crash. A plan the user chooses
  meanwhile is kept; a plan that is not on the machine is reported and
  nothing is switched; *Monitoring only* only logs.
- Rule actions `{ io_priority = "very_low" | "low" }` and
  `{ memory_priority = "very_low" | "low" | "medium" | "below_normal" }`.
  They only lower; the lowest request wins and each source rolls back its
  own, with the original read when RustWTM first takes the setting.

## Verification

`cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`,
`cargo doc` with warnings denied and the workspace tests pass on the
developer host (1243 passed, 23 ignored). `scripts/ci/verify-release.ps1
-Tag v0.38.0` checks the published assets. CI adds 0.37.1 as an upgrade
baseline, with the SHA-256 of its published MSI.

New tests:

- `wtm-sys`: the power plans listed with names and the active one among
  them (read-only); a power request created and dropped without being set.
- `wtm-policy`: entries parsed and validated, active while their apps run
  and for their hold, kept across a reload; game mode before the entries;
  plans by GUID or name; the TOML-preserving editors; the two actions
  parsed, refusing to raise.
- `wtm-service`: the keeper against a machine in memory (switch and back,
  the user's plan kept, a missing plan noted once, a refused switch, a
  failed restore kept for the next start, monitoring only, keeping awake
  and releasing on stop, game mode named by its plan); the two priorities
  on a real `ping` process, taking the lowest and rolling back per source.
- `wtm-gui`: the page with what is switched, adding, editing and removing
  an entry, an incomplete entry, monitoring only showing nothing in force,
  the entry buttons in view on a narrow page in all 26 languages; when the
  window keeps the screen on; the new texts and actions translated.

The page was rendered in English, Turkish, German, Russian, Tamil,
Japanese and Swahili, light and dark, wide and compact.

Not covered: the service has not run a `[[while_running]]` entry against
the real power plan on the developer host (the keeper's tests use a
machine in memory so the host's plan is never switched); a machine with
Modern Standby and a single plan.
