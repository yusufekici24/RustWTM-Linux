# Memory Guard

Memory Guard is an opt-in automation that trims the working sets of large
background processes under sustained physical-memory pressure. The service
uses Windows' working-set trim operation. Trimming reduces resident pages
and the process may fault those pages back in later.
[Windows working-set API](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)

New configurations and configurations without an explicit `enabled` value
leave Memory Guard off. Existing explicit settings are preserved, including
`enabled = true` in configuration files generated by earlier versions. See
[configuration](configuration.md#memory_guard) for thresholds and cooldowns.

## Bounded measurement

Run the Windows test from the workspace root:

```powershell
cargo test -j 2 --locked -p wtm-sys --test memory_trim_cost -- --ignored --nocapture --test-threads=1
```

It touches one byte per 4 KiB page in a fixed 32 MiB buffer, trims only its own
process, and compares ten paired baseline and trim trials with alternating
order. It measures the first revisit to the same pages. One local x64 Windows
debug-build run on 2026-11-19 produced these medians:

| Metric | Baseline | With trim |
|---|---:|---:|
| Working set immediately before step (MiB) | 34.64 | 34.64 |
| Working set immediately after step (MiB) | 34.64 | 2.38 |
| Working set after revisiting the buffer (MiB) | 34.64 | 34.48 |
| Private committed memory after step (MiB) | 35.72 | 35.72 |
| Time for the trim call (ms) | — | 5.20 |
| Time to revisit the buffer (ms) | 0.15 | 11.16 |
| Process page faults during revisit | 0 | 8,219 |

These are process-level measurements of immediate reclaim and refill cost.
The fault counter combines soft and hard faults. Foreground latency,
disk reads and sustained-pressure behavior need a representative workload
in an isolated lab with Windows' normal memory management as the baseline.
